# 设计：实例感知（哪个 dsh、连着谁、死了怎么办）

状态：提案（2026-08-30）。源于真实使用中的三次踩坑，全部发生在同一周。

## 1. 问题（全部来自实况，不是假想）

一台 Mac 跑了两个 bridle 身份（真环境 + 演示环境）之后，产品的"pair Macs"心智模型出现四道裂缝：

1. **同名不可辨。** 两条记录都叫 `alphadeMacBook-Pro`——顶部胶囊、机器列表、离线横幅全都分不清谁是谁。机器名默认取 hostname，同一台 Mac 上的第二个身份必然同名。
2. **断连时最显眼的出口是最具破坏性的那个。** Settings 里机器行的唯一动作就是 Forget（整行点击即进解除配对确认）；用户面对离线的第一反应真的就是"只能点 forget 了对吧"。Rename 在模型层存在（`AppModel.rename(machine:to:)`），但**没有任何 UI 调用它**——死能力。
3. **离线空态没有行动路径。** "The Mac is asleep, off your network, or Bridle isn't running on it." 三种可能并列，一个都没告诉用户怎么验证、怎么修。而事实上 app 手里已经握有能把三种可能收窄的证据（见 §3）。
4. **配对的真实单位与产品语言不一致。** 实际配对的是 bridle 身份（一个 `REINS_HOME` 的密钥对），身份指向一个 dsh 实例；"pair Macs" 在一机一实例时成立，多实例时心智断裂。

## 2. 设计原则（承接既有 UI 硬规则）

- **派生优先**：能从已有事实推导的，不新增任何落盘状态。
- **不断言不知道的事**（硬规则 #3）：收窄可能性只能用 app 真正持有的证据。
- **破坏性操作要能被找到、也要说清代价**（硬规则 #4）——但不该是唯一能被找到的动作。
- 产品语言保持 "Mac"，在需要处补充实例信息，不把"bridle 身份"这种实现词汇塞给用户。

## 3. 用户需要感知的四个事实与对应证据

| 事实 | app 已持有的证据 |
|---|---|
| A. 这条记录是谁 | 机器名、指纹、relay 设备 id；（提案后）harness 端口 |
| B. 现在连着哪条 | `active.machine.id` ✓ 已有 |
| C. 死的是哪一层 | relay 应答（machine offline = bridle 层没上线）、直连超时、`dshReachable`（bridle 在而 dsh 不在）——三层证据已经在 `status` / `ready` 帧里 |
| D. 死了怎么办 | 无。今日全靠用户脑补 |

## 4. 方案

### 4.1 身份可辨（A）——两层，都是派生

**冲突后缀（app 侧，零协议改动）**：当且仅当两条配对记录显示名相同，所有同名记录追加指纹首组：`alphadeMacBook-Pro · F943`。纯函数（`[PairedMachine] → 标签`），只影响显示，不落盘。单机器用户永远看不到后缀。生效面：顶部胶囊、机器列表行、离线空态与横幅里的机器名。

**harness 端口（协议可选字段）**：ready 帧新增可选 `harness: "http://127.0.0.1:3081"`（bridle 的 `state.dshUrl` 原样带出）。app 在机器详情与冲突场景可显示 `:3081`——比指纹更接近用户心智（"哦，是 demo 那个实例"）。老 bridle 不发此字段，app 不显示，向后兼容（协议 §14 的版本纪律照旧）。

### 4.2 Rename 从死能力变活（B/A）

Settings 机器行改为进入**机器详情页**：名称（可编辑）、指纹、harness 端口（有则显示）、最近一次连上的时间、Forget（红色、置底、保留二次确认与"单向性"说明）。行上的 swipe 保留 Forget，但整行点击不再直通解除配对。

### 4.3 分层诊断（C）——把并列猜测换成收窄陈述

离线空态按证据分三档写文案：

| 证据 | 空态首行 |
|---|---|
| relay 说 machine offline | "Bridle 没有连上中继——Mac 睡了，或 Bridle 没在跑。" |
| 隧道在、`dshReachable: false` | "Bridle 在线，但它连不上这台 Mac 上的 dsh。" |
| 直连超时且 relay 不可达 | 保留现状三选一（此时确实无法收窄，不装懂） |

### 4.4 急救卡（D）——只指导，不越权

离线空态在诊断行下方加一个可展开的 "On the Mac" 卡片，按 §4.3 的档位给对应命令：

- bridle 层死：`bridle status` 看真相；插件形态提示"重启 dsh 即可带起"；独立形态给 `bridle start`。
- dsh 层死：说明"Bridle 活着、harness 不在"，给 `dsh web` 与端口提示（harness 端口字段有则代入）。
- 文案明说 app 无法远程执行——隧道是唯一通道，机器侧死了只能人到场。这是诚实，也是安全边界。

### 4.5 明确不做

| 不做 | 理由 |
|---|---|
| app 远程拉起 bridle/dsh | 无通道（通道本身就是死掉的那层）；即便经 relay 加控制通道也等于把开机权交给电话，越权 |
| 同时连接多台机器 | 既有决策（每 socket 一份射频唤醒）不变 |
| 自动改 Mac 侧 machineName | 显示层能解决的不动源头；源头改名仍留给 `bridle.json` 手改或未来 CLI |
| pair 时自动加 " 2" 后缀落盘 | 记忆式方案；冲突消失后缀还赖着，派生方案冲突消失即还原 |

## 5. 落点

| 层 | 改动 |
|---|---|
| ios `Models.swift` | 冲突标签纯函数 + 单测 |
| ios `RootView` / `SettingsView` | 胶囊与列表用标签；机器详情页（rename 活化、Forget 降权重） |
| ios 空态 | 三档诊断文案 + 急救卡 |
| protocol / bridle | ready 帧可选 `harness` 字段（`docs/protocol.md` §ready 增补） |
| docs | `architecture.md` §9.2 增补一条硬规则引用本文件 |

## 6. 待议

- 急救卡命令文案是否区分插件/独立形态：bridle 自己知道自己是哪种形态吗？（runtime.json 没记形态；可加，或文案合并两种说法）
- `harness` 字段暴露 loopback 端口给已配对手机——无安全增量（配对方本就可经隧道调 `host.describe` 看到 cwd/home），但 review 时请专门过一眼。
